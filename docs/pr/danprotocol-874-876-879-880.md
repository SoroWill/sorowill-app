# Password-protected wills, beneficiary lookup, two-factor auth and custom branding

One branch for four Stellar Wave issues: #874, #876, #879 and #880.

## #874 — password-protected will access

**Done**
- `src/lib/willPassword.ts`: PBKDF2-SHA256 (210k iterations) + AES-256-GCM,
  random salt/IV, password policy, per-will lock storage and tab-scoped unlock.
  Only the salt, IV and ciphertext are stored; the password is never persisted.
- `WillPasswordGate` wraps the will detail page and prompts before rendering
  when a lock exists. `WillPasswordPanel` lets the owner enable or remove it.
- `docs/PASSWORD_PROTECTED_WILLS.md` documents the threat model: this protects
  the local view on a shared device, not the public on-chain record.
- Tests: `willPassword.test.ts`, `WillPasswordGate.test.tsx`.

**Not done**
- The UI copy is English-only (not yet in next-intl).
- Protection is per browser profile and cannot be recovered if the password is
  lost, by design.

## #876 — beneficiary lookup by address

**Done**
- `/inherit/lookup` searches the wills naming a Stellar address, shows each
  match with the beneficiary's share and links to the claim flow.
- Client-side pagination (6 per page) through `src/lib/beneficiaryLookup.ts`.
- `getWillsByBeneficiary` scans the contract and tolerates partial read failure,
  with the page warning that results may be incomplete.
- The lookup is linked from `/inherit` and added to the sitemap.
- Tests: `beneficiaryLookup.test.ts`, `get-wills-by-beneficiary.test.ts`.

## #879 — two-factor authentication

**Done**
- TOTP and SMS enrollment, verification, status and disable routes under
  `/api/auth/2fa/*`, with CSRF checks and rate limiting.
- Signed, HttpOnly cookies (10-minute enrollment, 30-minute verified, 30-day
  enrolled). Recovery codes are returned once and only hashes are kept; a used
  recovery code is consumed.
- `/settings/security` UI with QR code, SMS fallback and recovery-code display.
- SMS delivery through Sent (`SENT_API_KEY`, `SENT_PROJECT_ID`); without
  credentials, development logs the code and production fails loudly.
- `TWO_FACTOR_SECRET` signs the cookies; production refuses to start without it.
- `docs/TWO_FACTOR_AUTH.md` documents the flow and configuration.
- Tests: `totp.test.ts`, `twoFactor.test.ts`, `twoFactorRoutes.test.ts`.

**Not done**
- The verified cookie is not yet required by will operations (check-in, trigger,
  top-up, beneficiary changes). Enrollment and verification are complete; wiring
  enforcement into those routes is the remaining part of the issue.
- Enrollment is per browser, not per wallet across devices.

## #880 — custom domain and white-label branding

**Done**
- `getBranding()` reads `NEXT_PUBLIC_BRAND_NAME`, `_TAGLINE`, `_LOGO_URL` and
  `NEXT_PUBLIC_SITE_URL`, validating values and falling back to SoroWill
  defaults. Header, footer, metadata, Open Graph/Twitter tags and the `/verify`
  metadata use it.
- `src/proxy.ts` redirects configured aliases to `BRAND_CANONICAL_HOST` with a
  308, preserving path/query. Unknown hosts and localhost are never redirected,
  and the target never comes from the `Host` header.
- `docs/CUSTOM_DOMAIN.md` covers DNS, TLS (platform-terminated), Vercel steps
  and the redirect rules.
- Tests: `branding.test.ts`.

**Not done**
- No certificate automation in the app (handled by the hosting platform).
- `NEXT_PUBLIC_BRAND_PRIMARY_COLOR` is parsed but not yet applied to the theme.
